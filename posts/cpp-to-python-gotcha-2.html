C++ to Python Gotcha 2: Same OOP Words, Different Class Model

C++ and Python both support object-oriented programming, but they do not mean the same thing by a class. The syntax can look familiar while the runtime behavior is fundamentally different.

April 12, 2026 • 6 min read • C++ / Python

The Confusion

A lot of OOP vocabulary carries over cleanly from C++ to Python: classes, objects, methods, inheritance, encapsulation. That makes it tempting to assume the underlying model is basically the same.

It is not.

The important clarification is this: both languages support object-oriented programming, but the object model behind classes is different.

Short version: in C++, a class mostly defines per-object structure and behavior. In Python, a class is also a runtime object with its own attributes, lookup rules, and dynamic behavior.

What C++ Developers Usually Expect

In C++, when you write a member on a class, you are usually defining part of the layout of each object:

class Car {
public:
    std::string model;
    int year;
};

Car a;
Car b;

Each object has its own model and year. If state is meant to be shared, you must say so explicitly with static.

class Car {
public:
    static int number_of_cars;
};

That makes the default mental model very clear: member data is per-object, shared data is special.

What Python Actually Does

In Python, a name assigned in the class body is a class attribute:

class Car:
    wheels = 4
    features = []

Those values live on the class object itself. Instances look them up when they do not already have their own attribute with the same name.

a = Car()
b = Car()

print(a.wheels)  # 4
print(b.wheels)  # 4

That means the line looks class-shaped, but it does not mean the same thing it would in C++.

Why the Shared-State Bug Happens

The classic bug from the first post in this series comes directly from that model:

class Car:
    features = []

a = Car()
b = Car()

a.features.append("turbo")
print(b.features)  # ["turbo"]

A C++ reader sees something that looks like instance state. Python sees a class attribute referring to one shared list.

The mistake is not about OOP in general. The mistake is assuming that a Python class body declares instance storage the way a C++ class does.

Methods Also Behave Differently

Even methods are not quite the same concept.

In C++, a method is a member function with rules around overloading, virtual, const, and compile-time type checking.

In Python, a method is a function stored on the class that becomes a bound method when you access it through an instance.

class Car:
    def describe(self):
        return "car"

a = Car()
print(a.describe())

That flexibility is powerful, but it comes from a dynamic lookup model rather than fixed compile-time object layout.

Inheritance Feels Similar Until It Does Not

Both languages support inheritance, but the mechanics differ.

  1. In C++, inheritance is strongly tied to object layout, vtables, and compile-time rules.
  2. In Python, inheritance follows dynamic attribute lookup and method resolution order.
  3. Multiple inheritance is much more common in Python, which also means MRO becomes part of everyday design.

So yes, the OOP vocabulary matches, but the implementation model underneath it does not.

The Better Mental Model

If you are coming from C++, this framing is safer:

  1. C++ class: mostly a blueprint for per-object structure plus methods.
  2. Python class: a runtime object that can hold shared attributes, methods, and metadata, while instances get their own attributes when assigned.

That small shift in mental model explains a lot of Python behavior at once.

How to Write Python Without Fighting It

If you want per-instance state, initialize it in __init__ or with a dataclass.

from dataclasses import dataclass, field

@dataclass
class Car:
    model: str
    features: list[str] = field(default_factory=list)

If you want shared state, keep it on the class deliberately and name it as such.

class Car:
    supported_engines = ["V6", "V8", "EV"]

The key is not to write Python as if the class body were declaring instance fields in the C++ sense.

Key Takeaways

  1. OOP concepts transfer, but class semantics do not transfer unchanged.
  2. C++ defaults to per-object member state.
  3. Python class-body assignments create class attributes, not instance fields.
  4. Many Python surprises disappear once you remember that classes are runtime objects.
