C++ to Python Gotcha 1: When Object State Becomes Shared

One of Python's easiest traps for C++ developers is that state which looks like part of each object can actually be shared. The language is behaving consistently, but the mental model is different.

April 12, 2026 • 7 min read • Python

The Surprise

This post is the first in a short series about behaviors that surprise C++ developers when they move to Python.

One of the most common early surprises is this: state that looks like it belongs to each object can end up being shared across instances.

That is not how C++ objects behave. Let me show you why, and how to avoid the pitfall.

The C++ Mental Model

In C++, class member initialization is straightforward:

class Car {
public:
    std::string model;
    std::string size;
    std::vector<std::string> features;  // Each instance gets its own

    Car(const std::string& model, const std::string& size)
        : model(model), size(size), features() {}
};

int main() {
    Car ferrari("F430", "XL");
    Car honda("Civic", "Medium");

    ferrari.features.push_back("turbo");

    // honda.features is completely separate-still empty
    std::cout << honda.features.size();  // Prints: 0
}

In C++, each object gets its own copy of every member variable. features is not shared; it is part of the object's storage.

The Python Gotcha

Now look at a tempting Python translation:

class Car:
    model: str
    size: str
    features: list[str] = []  # Shared by all instances

ferrari = Car()
ferrari.model = "F430"
ferrari.size = "XL"

honda = Car()
honda.model = "Civic"
honda.size = "Medium"

ferrari.features.append("turbo")

print(len(honda.features))  # Prints: 1

In Python, class-level values are evaluated once when the class is defined. That means this list lives on the class itself and every instance sees the same underlying object until it overrides it.

When you call ferrari.features.append(...), you are mutating that shared list instead of creating instance-specific state.

The real mismatch: C++ developers instinctively read that field as per-object state. Python reads it as a class attribute.

Why Python Works This Way

  1. Class attributes are real objects that live on the class itself.
  2. Instances fall back to class attributes when they do not have their own attribute with the same name.
  3. Shared state is sometimes intentional for counters, registries, and constants.

This is not a bug. It is flexible, but it creates a sharp edge when you expect C++-style object storage semantics.

The Fix: Use dataclass with field(default_factory=...)

Modern Python gives you a clean way to express per-instance mutable state:

from dataclasses import dataclass, field

@dataclass
class Car:
    model: str
    size: str
    features: list[str] = field(default_factory=list)

Now each Car instance gets its own fresh list created by default_factory=list.

ferrari = Car("F430", "XL")
honda = Car("Civic", "Medium")

ferrari.features.append("turbo")

print(len(honda.features))  # Prints: 0

The key idea is simple: default_factory runs for each new instance, so the mutable object is no longer shared.

What About Immutable Types?

Immutable types like int, str, and tuple usually appear safe, but for a subtler reason than it first appears.

class Car:
    model: str = ""
    tires: tuple[int, ...] = (4,)

a = Car()
a.model = "Ferrari"
a.tires = (6,)

b = Car()
print(b.model)  # Prints: ""

This works because strings and tuples cannot be mutated in place. Assigning a new value creates an instance attribute that shadows the class attribute instead of mutating shared state.

With mutable types, in-place changes expose the sharing immediately:

class Car:
    features: list[str] = []

a = Car()
a.features.append("turbo")

b = Car()
print(b.features)  # ["turbo"]

The Clean Pattern

If you want per-instance state that always behaves predictably, initialize it inside __init__ or use a dataclass.

Option 1: Traditional __init__

class Car:
    def __init__(self, model: str, size: str) -> None:
        self.model = model
        self.size = size
        self.features: list[str] = []

Option 2: Dataclass

from dataclasses import dataclass, field

@dataclass
class Car:
    model: str
    size: str
    features: list[str] = field(default_factory=list)

Both approaches guarantee that each instance owns its own state.

Key Takeaways

  1. Class-level mutable objects are shared until an instance creates its own attribute.
  2. The trap is conceptual because the same line reads differently to a C++ developer and to Python.
  3. Use dataclasses or __init__ whenever you want per-instance mutable state.
  4. Shared class state is valid when intentional, but it should be explicit.

Side-by-Side Comparison

Here is the same scenario in both languages:

C++

class Car {
public:
    std::string model;
    std::vector<std::string> features;
    Car(const std::string& m) : model(m) {}
};

Car a("A"), b("B");
a.features.push_back("x");
std::cout << b.features.size();  // 0

Python with accidental shared state

class Car:
    features: list[str] = []

a = Car()
a.features.append("x")
b = Car()
print(len(b.features))  # 1

Python with safe per-instance state

from dataclasses import dataclass, field

@dataclass
class Car:
    features: list[str] = field(default_factory=list)

a = Car()
a.features.append("x")
b = Car()
print(len(b.features))  # 0
